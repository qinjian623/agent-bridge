## 通知

- 原生队列中仍有通知时，父线程处于 `active/idle` 不再导致 `ready=true`。只有匹配到原生 `userMessage.clientId` 才记录 `native_status=received` 和 `native_turn_id`；这表示进入原生轮次，不能称为模型已读。
- `parent_ack` 只确认父 agent 已处理事件，记为 `processed`。它可以来自对 `agent_result` 的独立处理，不再把原生发送记录直接改为 `received`。
- ACK 后持久记录 `queue_cleanup=pending`，后台精确查找该父线程、事件 clientId 和已有入队回执。回执缺失时，只允许从唯一的精确 clientId 匹配恢复回执。不会按正文匹配、清空队列或选择其他通知。
- 尚在队列的原通知可以撤回；已进入原生轮次的通知只记录 `already_started`，不删除历史或中断当前轮次。父记录暂停或关闭不阻止撤回，撤回过程不 enqueue、resume、steer 或 interrupt。
- 删除响应丢失、返回 false、回执冲突或没有接收证明时保留 `uncertain`。此后的自动检查仅查询队列和原生轮次，不再删除。首次删除前的连接或查询失败保持 `pending`，允许稍后安全重试。
- ACK 与发送回复并发时保留迟到回执；迟到发送或旧清理结果不能覆盖较新的 `removed/received`。清理按本次领取时间检查后才写回并更新原生发送队列。
- 旧版 `accepted` 不当作已读证明，只读重新核查；旧 `processed` 记录保留 ACK，另行检查是否仍有可撤回的原通知。原生历史最多查询最近 100 个轮次，超过范围仍未确认时保留未知，不重发。
- 正常初始化会补查 `processed + queue_cleanup=NULL`，涵盖旧 Broker 在新 worker 已添加列之后才 ACK 的情况；已有 `uncertain/removed` 等结果不重置。
- 新通知带事件时间，并说明不授权恢复已暂停的开发或重跑任务。

`deliveries` 增加 `native_status`、`native_turn_id`、`queue_cleanup`、`cleanup_last_attempt`，已有接口和状态字段保留。`native_status` 与 `status=processed` 分别表示原生接收情况和父 agent 处理情况。

## Bridge 子任务等待

- `JsonProcess.request()` 的同一个超时现在覆盖写入和响应等待，包含此前不受限的 `stdin.drain()`。超时记录方法和 `write/response` 阶段，清理等待项，不重发原请求。
- Worker 启动沿用既有 `task_timeout`。连接卡住时结束等待，未派发任务保持 `queued`，会话等待检查，不自动重启任务。
- 原生接收尚未确认时，任务超时、暂停或取消也会结束等待。不能确认执行结果的任务记为 `recovery_needed`，后续任务不启动；不把未确认的取消写成已取消。
- 原生已接收后继续使用现有中断流程和 `interrupt_timeout`，需要真实终态才能认定结束。`native_wait_ended` 记录阶段和原因，未改变模型、权限或本机超时配置。

这些修改不能修复报告中主 Codex 的六小时模型请求等待：Bridge 不持有主会话的请求对象，原日志也不能证明请求已实际发出或收到响应头。要区分发送、响应头、流活动和重试阶段，需要在 Codex 客户端记录这些事件并限制整个请求的等待时间。本次没有修改客户端配置。官方的 `stream_idle_timeout_ms` 仅描述 SSE 流空闲超时，不能拿来推断此次总等待的原因。[OpenAI 配置说明](https://learn.chatgpt.com/docs/config-file/config-reference)
